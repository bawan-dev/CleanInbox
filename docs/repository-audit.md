# Repository audit: pre-implementation baseline

> **Audit snapshot:** This document records the repository as it existed at commit `9f8ce18` on **2026-08-06**, before the Gmail draft-only implementation began. Later changes must not be read back into these findings.

The baseline stack was Next.js 16/React 19 running through vinext on a Cloudflare Worker, with Drizzle ORM and a Sites-provided D1 binding (`package.json`, `worker/index.ts`, `db/index.ts`, `.openai/hosting.json`). The only application routes were `GET /api/health`, `GET /api/messages`, and `POST /api/policy` (`app/api/health/route.ts`, `app/api/messages/route.ts`, `app/api/policy/route.ts`).

## Confirmed working functionality

- **Q1 — What worked end to end:** only the interactive **simulation** worked end to end. `app/page.tsx::Home` rendered `app/clear-inbox-app.tsx::ClearInboxApp`; users could search and filter demo messages, edit a proposed reply, mark it approved, escalate it, and mark it resolved. Those actions changed React state through `approveMessage`, `escalateMessage`, `archiveMessage`, and `addEvent`; they did not persist or contact an email provider. Separately, `lib/policy.ts::evaluatePolicy` implemented deterministic policy decisions, with seven baseline cases in `tests/policy.test.ts`.
- **Q5 — Narrow tenant-aware reads:** `lib/tenant-context.ts::resolveTenantContext` derived an email from `oai-authenticated-user-email`, required exactly one active `memberships` row, and supplied the resulting tenant ID to protected APIs. `GET /api/messages` scoped both `messages` and its `threads` join to that tenant, and `POST /api/policy` scoped its `tenantSettings` lookup. This was useful groundwork, not complete tenant isolation.
- **Q14 — Committed secrets:** a baseline repository scan found no recognisable OAuth credentials, API keys, bearer tokens, or private keys. `.gitignore` excluded `.env*` and `*.pem`. `mailboxes.credentialReference` in `db/schema.ts` was only an unused schema field; no token implementation or token values existed.
- **Q18 — Current text rendering:** demo message bodies in `app/clear-inbox-app.tsx::MessageThread` were interpolated as React text nodes. The baseline did not use `dangerouslySetInnerHTML`, so the hard-coded plain text itself was not executed as HTML.

## Partially implemented functionality

- **Q3 — Authentication:** `app/page.tsx::Home` read Sites-injected identity headers for display, and `resolveTenantContext` rejected missing headers for the two protected APIs. The page itself was not protected, and there was no application user model, sign-in/sign-out flow, secure session, middleware, or public authentication callback. A private Sites workspace header is deployment access control, **not public SaaS authentication**.
- **Q4 — Organisations and membership:** `tenants` and `memberships` existed in `db/schema.ts`, with roles `admin`, `approver`, `operator`, and `viewer`. There were no create/join organisation routes, membership-management routes, user IDs, invitations, tenant selection, or the required `OWNER`/`REVIEWER` role model. `ClearInboxApp::Sidebar` instead hard-coded “Northstar Goods” and “Alex Morgan”.
- **Q5 — Tenant isolation:** most customer tables in `db/schema.ts` carried `tenantId`, and several indexes were tenant-scoped. Coverage stopped at the two reads above: no service layer or tests proved isolation for mailboxes, credentials, drafts, approvals, settings writes, audit events, sync jobs, search, or analytics. `resolveTenantContext` did not join `tenants` to reject a suspended tenant. Child foreign keys referenced only a row ID rather than a composite `(tenantId, id)`, so the database did not prevent a child carrying tenant A's `tenantId` from referencing tenant B's mailbox, thread, message, draft, or approval if an insert path made that mistake. The mailbox uniqueness constraint was tenant-scoped, so one provider mailbox could also be attached to multiple tenants.
- **Q11 — Approval checks:** `evaluatePolicy` could require approval, but `POST /api/policy` trusted the browser-supplied `approvalRecorded` boolean. `approvalRequests`, `draftVersions.contentHash`, and `actionHash` existed in `db/schema.ts`, yet no server workflow created, checked, expired, revoked, or consumed them. `approvalRequests.draftVersionId` was nullable and did not bind all required message/thread/draft/version/hash facts. UI approval lived only in `ClearInboxApp`'s `approvedIds` state and did not hash the edited `DraftCard` value.
- **Q12 — Idempotency:** provider import uniqueness indexes and `actionExecutions.idempotencyKey` existed in `db/schema.ts`. No import, analysis, approval, audit, or provider-action service used them; no retry/reconciliation behavior or duplicate-request tests existed. Idempotency was therefore schema-only.
- **Q13 — Audit integrity:** `auditEvents` included `previousEventHash`, `eventHash`, a tenant/hash unique index, and no update/delete route. There was also no append service, server-authoritative hash calculation, database trigger, access-control route, or immutability test. The visible audit timeline came from `lib/demo-data.ts::initialAuditEvents` and `ClearInboxApp::addEvent`, so it disappeared on refresh. Audit protection was schema-only.
- **Q20 — Logging:** `lib/tenant-context.ts::jsonError` returned a generic 500 and logged only an error name, which was a reasonable narrow failure mode. There was no central redaction utility or tested policy for future OAuth, Gmail, AI, sync, or background-job logs, so protection against leaking bodies, tokens, and customer data was incomplete.

## Simulated or demonstration-only functionality

- **Q2 — Mocked and hard-coded behavior:** `lib/demo-data.ts` supplied every message, thread, analysis, draft, attachment, queue count, and audit event. `ClearInboxApp` initialized `messages`, `approvedIds`, `events`, and automation settings with `useState`; no UI action called an API. Tenant, staff identity, dates, counts, provider-like outcomes, and policy badges were hard-coded. The “Simulation” badge was accurate, but claims such as “Prioritised using tenant rules and full-thread context”, “100% Actions policy-checked”, “Scanned”, and a “complete, tenant-scoped history” were not backed by runtime services.
- **Q19 — Attachments:** `AttachmentRow` rendered hard-coded filename/type/size/risk metadata and could label an item “Scanned”, while `attachments` in `db/schema.ts` was unused. There was no upload/download path, MIME validation, scanner, parser, macro isolation, object storage, or attachment-content processing. Real attachments were neither processed nor proven safe.
- **Deployment state:** `GET /api/health` explicitly returned `mode: "simulation"`; `.openai/hosting.json` configured a D1 binding and the UI was deployable, but deployment did not turn any demo action into a mailbox operation.

## Missing functionality

- **Q6 — Real provider connection:** none of the three routes called an email provider. There was no provider client, sync worker, queue, callback, or webhook.
- **Q7 — Gmail OAuth:** no Google authorization URL, OAuth start/callback/disconnect routes, state/nonce/PKCE handling, code exchange, identity validation, scope tracking, refresh/revoke flow, or encrypted credential storage existed. Consequently there was no implemented OAuth callback to audit as secure.
- **Q8 — Reading real mail:** there was no Gmail API client, mailbox list/read operation, MIME parser, recent-message import, complete-thread retrieval, history cursor, duplicate reconciliation, retry logic, or persisted sync status. `GET /api/messages` could read pre-existing D1 rows but nothing populated them from Gmail.
- **Q9 — Creating real Gmail drafts:** there was no Gmail MIME builder, `users.drafts.create` call, provider draft ID, provider-success verification, timeout reconciliation, or user-facing real-draft result. The draft editor modified only component-local state.
- **Q10 — Provider side effects:** no route could send, forward, delete, archive, label, or otherwise modify a real mailbox. The archive button only changed local status and displayed “Archive remains simulated”. This negative result was safe, but it also means no Gmail draft-only workflow existed.
- **Q15 — Environment validation:** there was no environment schema, startup validation, feature gate, `.env.example`, or documented secret contract. `db/index.ts::getDb` checked only whether the D1 binding existed when called. Because `.gitignore` ignored all `.env*`, a future `.env.example` would also have been ignored unless explicitly re-included.
- **Q16 — CSRF, redirects, and OAuth state:** there were no auth/OAuth routes, so state validation, one-time consumption, expiry, user/tenant binding, redirect allow-listing, and callback error handling were all absent rather than demonstrably vulnerable. `POST /api/policy` had no CSRF mechanism or robust runtime request schema; the private hosting header was the only surrounding identity assumption.
- **Q17 — Prompt injection:** there was no AI provider, prompt builder, structured-output validator, trusted/untrusted context separation, or model retry/review path. The displayed analysis was hard-coded. Real email content therefore could not yet attack a model, but the required defenses were entirely missing.
- Also absent were durable user/tenant onboarding, protected application pages, mailbox connect/disconnect UX, credential revocation, manual sync, structured AI analysis, draft versioning APIs, approval execution, Gmail-draft creation, audit retrieval, retention/redaction jobs, tenant deletion controls, security/privacy placeholders, integration tests, and production runbooks.

## Security risks

- `POST /api/policy` performed a small manual shape check and accepted `approvalRecorded` from untrusted JSON. It must never be reused as authorization for a provider action.
- `lib/policy.ts::externalActions` treated only `reply` and `forward` as externally visible. Consequently `label`, `archive`, and `delete` could be classified as internal and allowed if enabled. `tenantSettings.autoLabel` defaulted to `true`, and both `OperatingMode` and the schema admitted `autonomous`; these defaults conflicted with the Gmail-only, no-label, no-archive, no-delete MVP boundary.
- Tenant membership was email-based and did not enforce tenant status. Database foreign keys did not encode tenant consistency, and the same provider account was not globally unique. Any future mutation route would have needed explicit, transactional cross-tenant checks.
- The baseline had no secure-cookie/session configuration, CSRF controls, OAuth replay controls, input schemas, content-retention controls, encrypted-token implementation, security headers, or CSP (`next.config.ts` was empty).
- Plain-text demo rendering was safe, but there was no HTML sanitizer, remote-image/tracking protection, or safe representation for real HTML mail. Attachment “Scanned” claims were unsupported.
- Audit hashes would have been caller-controlled without a central writer, and no redactor guarded future logs. Email bodies were required `textBody` rows with no expiry/redaction field or retention job.

## Production blockers

- **Q21 — Suitability for real business email:** the baseline deployment was **not suitable**. It had a deployable UI, D1 wiring, and useful schema/policy foundations, but lacked public SaaS authentication, secure organisation onboarding, provider integration, encrypted credentials, tested authorization, privacy controls, and operational failure handling. It must remain a simulation until those controls are implemented and verified.
- **Q22 — Exact blockers to a secure Gmail draft-only MVP:** 
  1. Real user authentication, secure sessions, protected pages/APIs, tenant creation/joining, and server-enforced owner/reviewer roles.
  2. Validated environment configuration and deployment secrets, plus authenticated encryption and redacted logging.
  3. Google OAuth with exact redirects, one-time expiring state bound to user and tenant, PKCE/nonce validation, minimum scopes, encrypted tokens, refresh, revoke, disconnect, and duplicate-account prevention.
  4. Conservative Gmail message/thread import with complete-thread retrieval, durable sync state, safe retries, tenant-scoped queries, and database-backed deduplication.
  5. Structured AI analysis and draft generation with strict validation and explicit untrusted-email boundaries.
  6. Durable draft versions and server-side approval integrity that binds tenant, message, thread, draft, exact version, content hash, approver, status, and expiry.
  7. Idempotent `users.drafts.create` execution with exact recipient/thread validation, provider response verification, ambiguous-timeout reconciliation, and no send/forward/delete/archive/label provider code.
  8. A server-written append-oriented audit trail; safe email HTML/remote-content handling; metadata-only attachment policy; body-retention/redaction and tenant-deletion controls.
  9. Automated coverage for authentication, role permissions, all tenant-owned resources, OAuth replay/association, token encryption, imports, prompt injection, approval staleness, duplicate draft creation, revocation, logging, HTML, and disconnect behavior.
  10. Reviewed D1 migrations, production configuration, Google test-account end-to-end verification, secret scanning, quality/build checks, and documentation that accurately distinguishes implemented behavior from remaining limitations.

Until those blockers are resolved, the accurate product description is: **a polished, private simulation with partial tenant-aware data and policy foundations—not a connected Gmail product**.
